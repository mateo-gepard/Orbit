# Threadmap CTO audit — 20 August 2026

**Scope:** complete repository and launch system: product UX, accessibility, client state, Firebase
data plane, Cloud Functions, MCP/OAuth, Google Calendar, authentication email, PWA/service worker,
CI/CD, staging, production evidence, privacy, deletion, observability, and operational recovery.

**Code baseline:** `a4331089f4786a70955844277da1e796ac4d6162` on `main`, audited with the
working-tree remediation described below. The working tree was not committed, pushed, promoted, or
deployed during this audit. Live production therefore remains unchanged.

**Decision:** **NO-GO for production promotion.** The remediated candidate clears the complete
local code, policy, build, and browser matrix described in this report. Production still has
external/manual blockers that source code cannot prove: a true staging plane, protected release
approval, provider configuration, legal/vendor evidence, real-device drills, monitoring,
restore/rollback evidence, and independent release authority. The repository intentionally keeps
the production workflow fail-closed until those prerequisites exist.

The authoritative operational checklist is [PRODUCTION_READINESS.md](PRODUCTION_READINESS.md), and
the evidence ledger is [RELEASE_DRILL_EVIDENCE.md](RELEASE_DRILL_EVIDENCE.md). This report explains
the engineering judgment behind that gate.

## Executive assessment

Threadmap is not a simple static productivity UI. It is a multi-mode, offline-capable application
with six security-sensitive boundaries:

1. account-scoped browser state and persistent Firestore cache;
2. Firestore, Storage, callable Functions, and scheduled push delivery;
3. Google Calendar-derived content and third-party authorization;
4. OAuth/MCP grants, refresh tokens, tool scopes, and downstream AI clients;
5. passwordless authentication email and recovery;
6. a split Vercel/Firebase release whose two planes must remain compatible during promotion and
   rollback.

The initial repository did not enforce those boundaries consistently. The highest-risk defects
were not cosmetic: a wrong-region quota call could fail every scrape route; account deletion could
be reversed by still-valid sessions; MCP grants could survive deletion; stale async callbacks could
recreate forgotten UID data; resumable uploads were not fully bound to the quota-charged size;
Google-derived event content could cross into MCP despite the product disclosure; legacy records
could become unreadable or unwritable under stricter Rules; and a web release could be promoted
against an incompatible backend.

The remediation converts these from convention into enforceable invariants. It also corrects the
interaction and visual defects that materially affected trust: inaccessible focus/contrast,
undersized touch targets, motion without preference handling, command-palette semantics, delete
and sign-out copy, MCP grant management, cold-route ownership, service-worker update discovery,
and mobile overflow.

The remaining NO-GO is deliberate. It is now predominantly an evidence and operating-model gap,
not permission to bypass the gate.

## Audit method and evidence standard

The assessment combined:

- repository-wide architecture and trust-boundary tracing;
- independent lifecycle/security, release/observability, frontend, and cross-slice red-team passes;
- current-tree reconciliation of every Critical and High finding in the 6–7 August historical
  audit;
- adversarial review of deletion races, account switching, upload sessions, token refresh,
  Calendar provenance, Firestore legacy documents, service-worker updates, and release topology;
- exact Node 22.23.2/npm 11.5.1 static, unit, policy, Functions, dependency, and license gates;
- Firebase Firestore/Storage Rules tests against emulators on Java 21;
- production-build browser smoke across desktop Chromium, Android-class Chromium, and mobile
  WebKit, including axe, console/page errors, real 404 behavior, keyboard access, route headers,
  overflow, and short-viewport reachability;
- read-only live production probes where appropriate, without changing provider state or user data.

Evidence labels used in this report:

- **Verified:** reproduced by a test, build, emulator, browser run, or live read-only probe.
- **Code-proven:** traced through all relevant call paths and guarded with focused tests.
- **External gate:** cannot be established from the repository and needs dated provider/operator
  evidence.
- **Accepted limitation:** intentionally narrower behavior whose UI and documentation state the
  boundary truthfully.

## Target architecture and non-negotiable invariants

| Boundary | Required invariant | Enforcement after remediation |
| --- | --- | --- |
| Account | No old account may write after switch, sign-out, forget, or deletion begins | Monotonic client generations, server tombstone checks, quiesce-before-clear, durable deletion job |
| Browser storage | UID-scoped data is never silently reopened or recreated after secure cleanup | Scoped keys, persistence suppression, IndexedDB termination/clear, cross-tab handoff, post-await guards |
| Firestore/Storage | A user can access only their own records and valid schema | Rules ownership checks, server ownership checks, lifecycle barrier, emulator regressions |
| Upload | Provider bytes cannot exceed the declared/quota-reserved size | Minimum size, `contentLength` binding, intent registry, expiry sweep, attach-time verification |
| Google data | Google-connected or Google-derived event content never enters launch MCP scope | Immutable provenance, conservative legacy markers, central DAL exclusion, cross-tool tests |
| MCP | Every client, token, refresh, tool, and mutation obeys current scope and account state | Current scope ceiling, tombstone/auth checks, client expiry, per-user revocation, idempotency barriers |
| Authentication | Public launch does not expose unverified password signup or password enumeration | Google + inbox-verified email link only; provider configuration is an external launch gate |
| Email | Unknown/known addresses receive indistinguishable public outcomes | Bounded provider work, response floor/jitter, generic acceptance, no credential links in logs |
| Push | Old account transports and late registrations cannot bind to a new/forgotten account | Owner generations, compensating cleanup, previous-UID teardown, server device ownership |
| PWA | Old clients discover updates without caching private content or forced reload races | Stable SW URL, release-keyed bytes/caches, cache admission policy, explicit activation, retry/re-arm logic |
| Release | One reviewed SHA identifies compatible web and Firebase planes | SHA health, guarded Firebase deploy, region/config contracts, staged compatibility checks, fail-closed topology |

## Launch-blocking defects closed in code

### 1. Region and cross-plane availability

- The scrape quota client called `us-central1` while the callable was deployed in
  `europe-west1`. The route failed closed with 503 unless a stale US Function happened to exist.
- The region audit omitted that runtime caller and falsely passed.
- All runtime callers now use one deployment constant; the region gate scans app and Functions
  runtime sources and rejects divergent/US references.
- Firebase remains `europe-west1`; Vercel candidate intent is `fra1`. Deployed identity is still an
  external verification gate.

### 2. Monotonic account deletion and account-state quiescence

- The deletion tombstone/job used to be removed immediately after Auth deletion even though a
  Firebase ID token can remain valid. Concurrent tabs could recreate “ghost” data.
- Deletion now leaves a minimal completed tombstone with scheduled 180-day expiry, excludes that
  document from bulk deletion, and keeps cleanup state until uploads are safely swept.
- Admin upload/item/MCP paths enforce an active-account barrier. Post-I/O idempotency and cleanup
  writes merge only while the account remains active.
- MCP grants, token families, client authorizations, and derivative records participate in account
  deletion. Settings exposes authenticated list/revoke operations.
- Client deletion distinguishes `completed`, `pending`, and ambiguous `unknown`; copy no longer
  claims completion when cleanup is queued or uncertain.

### 3. Browser privacy after sign-out, deletion, and account switching

- Persistent Firestore cache and UID-scoped Zustand/localStorage data could survive sign-out and,
  worse, be recreated by late snapshot/save callbacks after cleanup reported success.
- Secure cleanup now quiesces every account writer synchronously, terminates Firestore, clears
  persistent cache where available, suppresses persistence during scope reset, signals sibling
  tabs, and fails future sessions to memory-only mode if disk cleanup cannot be proven.
- Firestore, settings, Flight, FCM, foreground message handling, item rollback, tool revisions, and
  store rehydration use monotonic owner/generation guards. Adversarial tests cover late snapshots,
  writes, seeds, rollbacks, push tokens, and revision keys.
- Locally generated notifications that can contain item titles carry a non-visible owner marker.
  Account switch/sign-out invalidates in-flight delivery synchronously, enumerates and verifies
  closure of already-visible old-owner notifications, and never falls back to an unenumerable
  plain browser notification for private content.
- Integration, notification, and local-device cleanup outcomes are reported separately; the UI no
  longer makes a broad privacy claim after a partial failure.

### 4. Upload quota, ownership, and cleanup

- A caller could reserve zero/small bytes and receive a resumable provider session whose actual
  upload was not bound to that size. Attach-time rejection happened only after storage cost.
- Upload initiation now requires a positive bounded size and binds provider `contentLength` to the
  quota-charged value. Active-session limits, origin checks, lifecycle tombstones, ownership, final
  object size, and attachment paths are revalidated.
- Cleanup keeps a barrier when the object is absent on the first sweep, repeats hourly through the
  provider session window, and releases reservations idempotently only at the safe terminal point.

### 5. MCP/OAuth authorization integrity

- Dynamic client registration, authorization, access-token validation, refresh rotation, and tool
  advertisement now reapply the current server-wide scope ceiling. Legacy broad clients cannot
  retain write/delete authority merely because production is switched to read-only launch policy.
- Production launch policy is `threadmap.read offline_access`, without loopback redirects or extra
  callbacks. Write/delete require a separate reviewed policy change.
- Dynamic clients are source-limited and expire. Authorization list/revoke is per-user and
  idempotent. Deletion and revocation use durable barriers.
- Staging OAuth consent is derived from the validated issuer origin rather than hard-coded to
  production.
- Consent now enumerates the actual secondary data exposed by `threadmap.read`, including
  attachment metadata, wishlist, school results, focus logs, briefing history, dispatch plans, and
  selected settings. File bytes are not implied.

### 6. Google Calendar data boundary

- Imported Google title, description, and timing data were stored as ordinary items and returned by
  MCP reads even though the product claimed exclusion.
- Calendar imports now stamp immutable origin provenance. Every detach/conflict path preserves it.
- The MCP DAL centrally excludes current and conservative legacy Google markers from direct reads,
  lists, search, agenda, tags, files, relations, mutations, and delete previews. Pagination advances
  over hidden raw documents without leaking them or looping.
- Threadmap-created events become excluded while connected to Google too. Consent and Settings copy
  state that narrower rule instead of promising origin inference the legacy data cannot prove.
- Google Limited Use and manual consent-removal limitations are stated in the legal/consent surface;
  final legal/provider approval remains external.

### 7. Authentication and email abuse boundary

- Direct password signup exposed the unavoidable Firebase `EMAIL_EXISTS` distinction, granted a
  session before inbox control, and allowed address squatting.
- Launch authentication is now Google or inbox-verified email link. Password callbacks and public
  password/reset surfaces are removed. Firebase console enforcement—disable password auth, enable
  email-link/Google, enumeration protection, App Check/reCAPTCHA—is a mandatory release gate.
- The server email endpoint applies App Check, quotas, idempotency, bounded input, safe branded
  action hosts, non-production fail-closed origin configuration, response timing/jitter, and generic
  acceptance. Provider/action-link failures on reset do not create a public existence oracle.
- Sender DNS, suppression, link-scanner behavior, Resend retention/transfer posture, and monitored
  support handling require real evidence before GO.

### 8. Firestore legacy compatibility and data integrity

- Strict new Rules initially rejected ordinary updates to legacy `status: inbox`, missing revision,
  or unknown-field documents the client still intentionally read.
- Rules now permit unchanged legacy state and normalization without permitting a client to invent
  unknown fields. Client writes converge legacy `inbox` to `active`, preserve future fields where a
  full merge is intended, and keep ownership/type/status/revision constraints.
- Active and archived subscriptions are independently bounded so archive churn cannot displace the
  working set. Cloud recovery mirrors are bounded/deduplicated; local-only mode retains its full
  local source of truth.
- Historical Critical/High functional regressions—auto-archive restore, progress dilution, rapid
  habit toggles, European price parsing, mention/date parsing, fuzzy parent selection, recurrence
  explosion, conflict recovery, sticky archive geometry, auth-loading deadlock, and Abitur
  calculation coverage—were rechecked against current implementations and regressions and retired.

### 9. PWA/update correctness and cache privacy

- The service worker now rejects private, `no-store`, or `Set-Cookie` responses from runtime caches.
- Cache identity uses release SHA while `/sw.js` remains a stable, non-cacheable discovery URL.
- Update checks recover after initial registration/update failures, attach to already-installing
  workers, retry on foreground/network/hourly triggers, and re-arm a deferred waiting worker.
- Activation is explicit. Session-storage markers are best-effort with an in-memory fallback;
  controller changes reload only the intended release path.
- Briefing schedule messages use monotonic generations and acknowledged clear semantics so a queued
  old-owner update cannot resurrect notifications after secure sign-out.

### 10. Frontend, responsive behavior, and accessibility

- Focus rings use opaque readable tokens; coarse/mobile controls meet the 44 px target across
  audited surfaces; placeholder/copy/accent contrast uses WCAG luminance rather than YIQ heuristics.
- Reduced-motion behavior covers global transitions and bespoke Flight/completion animation paths.
- Flight cold load waits for the correct account owner. Task selection/completion overlap and habit
  multi-day toggling are serialized without dropping input.
- Command bar listbox/combobox semantics, active descendant, create option, and keyboard navigation
  were corrected. The global Ctrl/Cmd+K listener now lives in the always-mounted shortcut layer,
  so a closed/unmounted palette can actually open.
- Settings distinguishes queued/unknown deletion, secure sign-out/forget-device outcomes, Calendar
  revocation, and MCP grant loading/error/retry/revoke states.
- Mobile overflow, short-viewport bottom reachability, focus restoration, responsive targets,
  briefing/loading contrast, and Flight accent foreground were added to automated browser gates.

## Accepted product limitations and bounded debt

These are not hidden behind optimistic copy:

- **Habit reminders:** exact per-habit reminders are device-local and require an authenticated
  Threadmap tab to remain open. Cloud morning/evening briefings can use push with the app closed;
  per-habit background push would require a separate indexed scheduling/data-minimization design.
- **Subscription ceilings:** the live client subscribes to at most 5,000 active and 1,000 archived
  records per account. This is an explicit scale ceiling, not complete pagination. Product/enterprise
  growth beyond it needs a paginated/query-specific client model.
- **Client telemetry:** privacy-sensitive browser error/analytics collection is intentionally absent
  until a provider, redaction schema, lawful basis, retention, and alert owner are approved.
- **Functions artifact identity:** web health reports exact SHA, but Firebase Functions do not yet
  expose independently signed build metadata. The workflow deploys both planes from one candidate
  and tests compatibility, but stronger Functions provenance remains worthwhile.
- **Machine accessibility coverage:** axe and keyboard smoke cannot replace real VoiceOver/TalkBack,
  zoom/reflow, cognitive, and real-device review.

## External/manual NO-GO register

The following require named owners, timestamps, and immutable evidence; source changes alone cannot
close them:

1. **True staging topology:** deploy the exact SHA to `threadmap-staging-9e0b6` and a genuinely
   staging-configured HTTPS web origin. Exercise sign-in, read/write, uploads, MCP/revoke, deletion,
   and old/new compatibility. Feed immutable results into a separate protected production job.
2. **Release governance:** prove `main` auto-deploy is disabled, configure a protected GitHub
   `production` environment with independent approval, restrict branches, test concurrency, and
   migrate the residual Firebase CLI token to narrowly scoped workload identity.
3. **Live deployment identity/residency:** the observed production deployment still reports old
   `iad1` execution and old headers/service worker. Only promotion plus exact-SHA `/api/health`
   verification can prove `fra1` and the new contract.
4. **Firebase controls:** prove App Check enforcement, authorized domains, password auth disabled,
   email-link/Google enabled, enumeration protection, abuse controls, delete protection, PITR,
   backups, restore rights, and a synthetic staging restore.
5. **Storage and tenant isolation:** apply/inspect production CORS, drill resumable cancellation and
   unapproved-origin denial, and perform two-account negative tests across Rules, exports,
   attachments, push, MCP, and deletion.
6. **Email operations:** prove Secrets bindings, DKIM/SPF/MX/DMARC, inbox delivery, one-time/expired
   link behavior, scanner compatibility, suppression, complaint/bounce alerts, monitored support,
   Resend retention/tracking settings, DPA/subprocessors, and international-transfer approval.
7. **Google and MCP:** exercise real Calendar connect/sync/conflict/disconnect and manual consent
   removal; connect a real approved MCP host, inspect consent, invoke every enabled launch tool,
   revoke, and prove the old token fails without affecting a second user.
8. **Privacy/legal:** approve controller identity, mail/postal contacts, Privacy/Terms/translations,
   lawful bases, retention, age policy, DPAs/SCCs, and the subprocessor/data-flow register.
9. **Observability/continuity:** prove a durable signed log drain or approved monitoring path,
   exact-SHA multi-location synthetic, 5xx/timeout/security/budget alerts, Core Web Vitals baseline,
   60-minute or traffic-based observation, restore, rollback, and after-hours ownership.
10. **Human validation:** real Chrome/Android/iOS PWA update/offline/draft tests, assistive-technology
    review, independent security/tenant review, and explicit release-authority sign-off.

## Go/no-go rule

The release authority may record **GO** only when all of the following refer to the same full
40-character SHA:

- the final repository gates, production build, browser suite, and manual local pass are green;
- true-staging authenticated and negative-path evidence is green;
- every item in `PRODUCTION_READINESS.md` has a named owner, timestamp, and evidence link;
- the protected workflow verifies the staged artifact and compatible Firebase plane before human
  production approval;
- the final alias passes exact-SHA, region, quota, App Check, OAuth, and runtime-error checks;
- rollback and incident owners are online for the observation window.

Any code, environment, Rules, Functions, or configuration change invalidates artifact-specific
evidence. A red or missing gate is **NO-GO**, not an invitation to waive the test inside the release
job.
